# Design

## Context

See `proposal.md` for motivation and scope. The current hub is generated by `mc_hub_world.py` as vanilla commands plus a datapack, then installed by `mc_hub_deploy.py`. Destination bays occupy the existing managed platform, use stable slot coordinates, and preserve an unwaxed owner-label sign. The datapack already enforces Adventure mode, harmless hub gamerules, cooldowns, and trigger-based requests; the host controller remains the only component that validates destination lifecycle actions.

The hub configuration and state files are private host-side JSON, while player-facing state can persist in the hub world's scoreboard and block entities. Deployment already distinguishes initial creation from explicit `--rebuild`, so geometry changes must use that boundary.

## Goals / Non-Goals

**Goals:**

- Add independently enableable community, reward, game, exploration, utility, collectible, and event regions.
- Keep player-facing content inert and preserve the existing controller trust boundary.
- Persist per-player claims, progress, records, and discoveries across hub restarts without introducing a database or external service.
- Expand the managed world outside the current destination-bay footprint rather than rewriting bay interiors.
- Make explicit rebuilds safe for existing owner labels and stable destination mappings.
- Give each feature a bounded cleanup, reset, and disable behavior.

**Non-Goals:**

- No destination-server plugin, mod, or container lifecycle redesign.
- No visitor access to RCON, Podman, operator permissions, or controller configuration.
- No unrestricted player-built plots or general-purpose editable terrain.
- No automatic migration that silently changes an already deployed world.
- No guarantee that rewards reproduce items or progression from destination servers.
- No web moderation UI or cross-server persistence service in this change.

## Decisions

### Use the existing generator/datapack boundary

Static structures, signs, display cases, utility stations, course geometry, and reserved event areas will be generated by `mc_hub_world.py`. Per-player claims, cooldowns, course state, discoveries, and cleanup loops will be datapack functions returned by `datapack_files`. `mc_hub_deploy.py` will continue to install the generated datapack only during deployment/rebuild operations. This reuses the current vanilla-only architecture and avoids adding a second runtime service.

### Extend the platform instead of consuming destination bays

The existing 128 bays use the x=0..255, z=16..143 grid. The new commons will occupy a separately managed extension north of that grid, with an explicit connector replacing only the current outer boundary where needed. New feature coordinates will be declared in one bounded layout map and tested for overlap with every stable bay, portal selector, owner-label position, and existing control sign. The original bay coordinates and slot mapping remain unchanged.

### Persist state in scoreboards and namespaced block entities

The datapack will use namespaced objectives for the hub day counter, daily-present claim day, activity cooldowns, game records, and collectible discoveries. Scoreboards are already persistent in vanilla worlds and naturally distinguish player identities. Static displays and submissions will use dedicated block-entity areas; no arbitrary player text will be converted into a command string. State names will be versioned so future datapack changes can migrate or reset only the relevant feature.

### Use trigger claims for player-specific interactions

Daily presents, scavenger completion, game starts, and similar actions will use enabled per-player trigger objectives or equivalent bounded interaction checks. The tick function will consume each request once, validate the player's location and cooldown, then clear the request before granting an outcome. This prevents a physical chest from becoming a shared unlimited reward source and matches the existing trigger pattern used for destination requests.

### Make the daily present a claim point, not a shared loot chest

The visible daily-present chest will be decorative or locked to ordinary players; a nearby claim sign/button will request the daily reward. A claim is accepted only when the player has not claimed during the current hub-day counter. Rewards will be defined in a validated, bounded configuration and compiled into explicit item grants. Invalid entries disable only that reward entry and produce an administrator-visible deployment error or warning.

### Separate editable messages from managed displays

The community area will contain a dedicated sign wall whose backing blocks are the only blocks that can accept supplied signs. The surrounding floor, walls, notices, suggestion channel, and curated displays remain managed and protected. Administrator notices, lore, and showcase text will be generated as inert plain-text components; player notes will never be used as click-event or command payloads. A separate suggestion container will hold written submissions for manual administrator review.

### Reserve fixed game and event contracts

Each game will have a fixed start region, finish region, reset region, scoreboard contract, and cleanup function. Event spaces will have explicit bounds and time-limited temporary entities or effects. The first implementation can ship a subset of the listed games, but the layout and datapack contracts will allow additional games to be added without changing destination bays or shared authorization logic.

### Treat feature configuration as deployment-time configuration

Feature enablement, reward allowlists, display text, and event defaults will be read from the existing private hub configuration or safe built-in defaults and validated before generation. Changing configuration will not mutate the running world during a controller poll. Operators must invoke the explicit deployment/rebuild path, and the deployment output will report disabled or invalid optional features.

### Preserve trust boundaries

Only existing administrator-authenticated controller requests may start, stop, or transfer destinations. Hub feature triggers will be namespaced and limited to harmless local effects, bounded grants, or per-player records. No player-authored text, reward item, scoreboard value, or event interaction will be allowed to produce a host command, RCON command, operator grant, or arbitrary `function` call.

## Risks / Trade-offs

- The current platform has no spare horizontal space, so extending the world increases generated commands, forceloaded chunks, and rebuild time. Keeping the extension separate avoids bay migration at the cost of a larger hub footprint.
- Vanilla scoreboards are persistent but awkward to inspect and have finite display ergonomics. They avoid a new persistence service but require careful objective naming, reset, and migration rules.
- Sign walls and shared displays are harder to moderate than a web form. The design limits content to a dedicated area and keeps suggestions manual; automated moderation is out of scope.
- A physical claim chest cannot safely enforce one reward per player by itself. The claim-point interaction is less literal than a normal loot chest but provides the required per-player bound.
- Rebuild preservation depends on strict coordinate and `keep` assertions. Geometry tests MUST fail if a new feature touches an owner-label position, portal selector, or managed destination control.
- A failed optional feature can leave unused reserved space. Independent feature flags and explicit deployment diagnostics favor safe partial availability over a monolithic all-or-nothing rebuild.
